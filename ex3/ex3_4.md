Sensing: Using the joint state measurements (stored as q_).

TrajectoryPublisher generates cartesian target from user choice (circle, triangle, line, test_error)
    - Why test_error? Because we need a way to test the error handling for trajectory planner, and the trajectory_type parameter doesn't allow strings not included in the list of valid trajectories

JointController reads the joints, target trajectory, computes feedback error, adds feedforward (optional) and sends the commands to ros.

Reactivity: Highly reactive, no complex reasoning.
Only input handling

Behaviors: Selected conditionally by user, no subsumption/other automated behavior selection except for hold-position fallback.

Data rates: 
- Controller 1000 Hz (franka_controllers.yaml)

- Trajectory publisher 10 Hz (trajectory_publisher.cpp shows timer period at 100ms)

Safety features:
- URDF joint limits for effort, velocity, position
- Cannot publish invalid trajectory, and if done, hold position.


Architecture: Sense-act (reacts to sensor readings, no world sensing), control hierarchy as follows:

1. Supervisory layer (user)

The user selects trajectory_type and use_feedforward through ROS parameters.
This changes the active behavior at runtime.

2. Trajectory-generation layer

TrajectoryPublisher runs the selected behavior: circle, line, triangle, or error/hold behavior.
It computes Cartesian position and velocity, then converts them to joint-space position and velocity using IK.
It publishes trajectory_point.

3. Joint-control layer

JointController reads measured joint positions and the desired joint trajectory.
It computes velocity commands using proportional feedback, optionally plus feedforward:

It sends velocity commands to ros2_control.

4. Hardware/simulation layer

controller_manager executes the controller and interfaces with Gazebo.
Gazebo applies the joint commands and produces new joint-state measurements
